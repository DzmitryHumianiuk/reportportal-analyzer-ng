Автоанализ падений тестов: исследование и план имплементации

Два раунда исследования (анализ legacy-анализатора + greenfield-консилиум) и готовый пакет спецификаций для мультиагентной разработки нового микросервиса без ElasticSearch.

Материалы: ~/scripts/analyzer-ng-plan/ · CONTEXT.md · specs/01–04 · MASTER_PLAN.md (≈3 900 строк)

TL;DR. В legacy-анализаторе OpenSearch делает меньше, чем кажется: только генерацию кандидатов (BM25 more_like_this) и ~9 score-фич — реальный матчинг уже на Python. Новый сервис analyzer-ng строится на PostgreSQL + pgvector с парадигмой «fingerprint → группировка на уровне лонча → каталог failure modes → калиброванный LightGBM (текст + метаданные) с правом воздержаться», плюс опциональный локальный SLM (Ollama, Qwen3-4B) в четырёх строго ограниченных ролях. Drop-in замена для docker-compose ReportPortal: контейнер сам создаёт схему в PG при первом старте; OpenSearch больше не нужен.

Часть 1 — Что делает текущий анализатор

service-auto-analyzer — Python-микросервис на RabbitMQ RPC (очереди index / analyze / suggest / cluster / search / train_models). В OpenSearch попадают только ERROR-логи: ≤20 на test item, без почти-дублей, предобработанные, — один документ на test item с nested-массивом логов и ~20 производными текстовыми полями. Индекс — на проект, один шард, стандартный анализатор.

Пайплайн двухступенчатый:

  1. OpenSearch: мультиполевой more_like_this (BM25) → top-K кандидатов + score.
  2. Python: ~40 фич (из них лишь ~9 — от BM25-скора; ~15 — sklearn TF-IDF cosine, это и есть тонкое сопоставление) → XGBoost-классификатор match/no-match. Кластеризация — полностью Python. Хранилище моделей уже абстрагировано (FS/MinIO/S3).

Ключевой вывод: «убрать ES» = заменить лексический top-K ретривер и одну score-фичу. Главный риск — ловушка score-фичи: все обученные модели (глобальная + per-project) привязаны к распределению BM25-скоров OpenSearch; смена ретривера требует переобучения и ре-валидации всего парка.

ЭкспертВердиктСуть

Часть 2 — Greenfield-консилиум: как строить «с нуля»

Четыре роли (векторный ретривал, локальные SLM, AIOps SOTA, главный архитектор) сошлись на трёх out-of-the-box рычагах, которые важнее выбора базы:

  • Метаданные сильнее текста. Продакшен-системы (Meta, Google, Atlassian, Launchable, Develocity) триажат по retry-исходам, истории флакинесса, ко-падениям, близости изменений — а не по тексту лога. Всё это дешёвые SQL-агрегаты.
  • Group-then-classify. Один сбой инфраструктуры → 50 одинаковых падений → один диагноз на группу внутри лонча; человеческий фидбэк становится в ~10× эффективнее.
  • Knowledge-base-first. Единица знания — курируемый failure mode (центроид + шаблоны + метка + purity + заголовок), а не сырой размеченный лог. Поиск по сотням центроидов; cold-start решается стартовым каталогом из 50 универсальных режимов.

Хранение: единогласно PostgreSQL

pgvector (≥0.8, iterative scans) + FTS в той же базе. Решающий аргумент — не бенчмарки, а транзакционная консистентность метки и вектора (переразметка видна ретривалу мгновенно) и ноль лишних stateful-контейнеров. Прецедент — Sentry: fingerprint → эмбеддер → pgvector HNSW, sub-100 ms. Отвергнуты: выделенные векторные БД (dual-write = фабрика багов), Milvus/Weaviate/Chroma (ops), DuckDB-VSS (экспериментальная персистентность). Parquet/DuckDB — холодный тир (v2+).

Локальный SLM: четыре роли «да», остальное «нет»

РольВердиктПочему
Классификатор✕GBM на своих метках точнее и в ~10⁵× дешевле; zero-shot SLM на 5-классовой лог-задаче — <10–34 % accuracy.
Судья top-K (gated)✓Только на низкоуверенных 10–20 % кейсов; retrieval-augmented Qwen3-4B: 56 → 95.6 %. Выход — enum через constrained decoding.
Объяснитель✓ первымЧистый UX, решение уже принято классикой; verbatim-цитаты проверяются substring-валидацией.
Экстрактор (JSON из лога)✓Root exception, слой (тест/приложение/инфра) → фичи для GBM; кэш по template-hash.
Cold-start рубрика✓Вторая линия после seed-каталога; метки помечаются «AI-suggested».
Reasoning-режимы / LoRA / агенты✕Прямые бенчмарки: reasoning не помогает (местами вредит); агентный RCA ≈ 11 % solve rate; LoRA — ops-взрыв.

Модели для бандла: Qwen3-4B (Apache-2.0) или IBM Granite 4 Micro. Логи — недоверенный ввод: constrained decoding, нонс-конверты, LLM никогда не подтверждает метку сам.

Итоговая архитектура analyzer-ng

логи ── AMQP (index) ──► PG: test_item / failure_signature (partitioned by project)
        │ on FAIL (async)
        ▼
 Drain3-шаблоны → signature doc → эмбеддинг (ONNX e5-small int8, 384d)
        ▼
 [1] группировка в лонче: exact-fp бакеты + cosine θ=0.83; burst → prior SI
        ▼
 [2] матчинг: error_hash exact → KB failure modes (0.6·cos + 0.25·Jaccard
     + 0.15·fp) → гибридный ретривал (FTS + pgvector, RRF k=60) top-20
        ▼
 [3] решение: LightGBM, 39 фич (similarity + retry/flakiness/co-fail/env),
     калибровка; τ_auto=0.75 → авто-метка; τ_suggest=0.45; ниже → TI (abstain)
        ▼                                ┌ Ollama-сайдкар (opt-in, async):
 suggestion → RP UI                      │ explainer · extractor · judge ·
 confirm/correct → label_event ──────────┘ cold-start; kill-switch по метрикам
        ▼
 переобучение GBM (каждые 100 событий / ночью; ship-gate по replay-eval)

Метки: PB product bug AB automation bug SI system issue ND no defect + TI как явный «воздержался».

Главные риски (из риск-реестра): дрейф wire-формата (RP может строго валидировать ответы — ловится G1/G5); гонки Drain3-state (CAS + single-writer per project); латентность эмбеддинга на слабых CPU (batch + деградация до lexical-only); дрейф train/serve фич (снапшоты в suggestion.features — обучение читает только их); расползание LLM-ролей (новая роль = сначала изменение спеки).

Сгенерировано по итогам двух исследовательских раундов с параллельными экспертными агентами; источники и бенчмарки перечислены в полных отчётах внутри спеков и в истории сессии.
