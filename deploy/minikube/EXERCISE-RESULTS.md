Root causes (one line each):
- **#1** — the engine matched seed/KB modes but never wrote `mode_membership` (the seed
  `mode_id` was discarded; no `add_members` call) and the lazy mode's `emb_model_ver`
  stayed NULL so `update_purity`'s centroid EWMA was a no-op.
- **#2** — a cold-phase debounce marker set by an early cold retrain attempt silently
  "debounced" every later retrain (including explicit `train_models`) for an hour; and
  `/health` read a static `gbm_model_ver` never updated after a model shipped.

Post-fix SUMMARY (all six stages): `PASS PASS PASS PASS PASS PASS`.

## Product findings

**FINDING #1 — KB-mode learning loop cannot bootstrap (`mode_membership` never written).**
Seed rule-matches create the per-project `failure_mode` candidate row and apply the
prior to the decision, but `mode_membership` is never inserted (0 rows), so
`suggestion.matched_mode_id` is never set and `failure_mode.purity/support/centroid`
never move. Spec contract `KBStore.spawn_candidate_mode` (02-database.md §4.3) requires
inserting membership rows; image `eb2343e` inserts the mode but not the membership.

**FINDING #2 — GBM retrain is a no-op.** With cold-gate (≥50) and retrain trigger
(N=100) both satisfied and balanced per-class data, neither the auto-trigger nor an
explicit `train_models` publish produces a `model_artifact`. The handler logs
`train_models: scheduling background retrain` but no trainer runs and no model/`gbm_model_ver`
appears. (`TrainInfo.model_type` is an int enum 1/2/3 on the wire — string values 422.)

**MINOR** — noisy pika reply-publisher `ConnectionResetError(104)`/`StreamLostError`
reconnects; RPC replies still succeed. Cosmetic.
